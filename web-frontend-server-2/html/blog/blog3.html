End-to-End Cloud Monitoring with Prometheus & Grafana

You can't operate what you can't measure. Prometheus pulls metrics from every service; Grafana turns them into charts anyone can read.

A cloud system can have dozens of containers starting and stopping all the time. If you only find out about a problem when users complain, it's already too late. Prometheus collects metrics as time series, and Grafana visualizes them on live dashboards.

Prometheus's pull-based model

Instead of each service pushing its metrics somewhere, Prometheus actively pulls (scrapes) them on a fixed interval, say every 15 seconds, from each target's HTTP /metrics endpoint. This has three advantages:

  • You know immediately when a target goes down, because the failed scrape shows up in the up metric.
  • Services don't need to know where Prometheus lives; they just expose an endpoint.
  • Adding or removing targets is a matter of central configuration.

Each metric is a series of timestamped values with labels, for example http_requests_total{method="GET", status="200"}.

Exporters: a bridge to everything

Not every piece of software ships with a /metrics endpoint. Exporters are small processes that sit in between and translate metrics into a format Prometheus understands:

  • node_exporter: CPU, memory, disk and network of the host.
  • cAdvisor: resource usage of each container.
  • nginx-prometheus-exporter: Nginx connections and requests.
  • blackbox_exporter: checks from the outside whether a URL responds.
prometheus.yml
global:
  scrape_interval: 15s

scrape_configs:
  - job_name: "node"
    static_configs:
      - targets: ["node-exporter:9100"]
  - job_name: "containers"
    static_configs:
      - targets: ["cadvisor:8080"]

About target namesWhen everything runs on the same Docker Compose network, services can reach each other by service name, such as node-exporter, instead of an IP address.

PromQL: asking your data questions

PromQL is Prometheus's query language. A few queries you'll use all the time:

PromQL
# Which targets are not responding?
up == 0

# CPU usage in percent, averaged over 5 minutes
100 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100

# Requests per second by status code
sum by (status) (rate(http_requests_total[1m]))

The rate() function matters a lot: counters only ever go up, so what you usually want is how fast they grow, not the absolute number.

Grafana: turning numbers into a picture

Grafana connects to Prometheus as a data source, and each panel on a dashboard runs one PromQL query. A good dashboard answers “is the system OK?” within five seconds of looking at it.

  • Put the most important metric in the top-left corner.
  • Use variables to filter by host or container instead of duplicating panels.
  • Import a community dashboard, such as “Node Exporter Full”, and tweak it from there.

Alerting before your users notice

Alert rules are written in PromQL. When a condition stays true long enough, Prometheus sends the alert to Alertmanager, which groups and deduplicates it and routes it to email, Slack or Telegram.

alert.rules.yml
groups:
  - name: basics
    rules:
      - alert: ServiceDown
        expr: up == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.job }} has not responded for over 1 minute"

What should you measure?

Two popular methods help you pick metrics without drowning in them:

  • RED for services: Rate (requests), Errors (error rate), Duration (latency).
  • USE for resources: Utilization, Saturation, Errors.

For MyMiniCloud, start with three questions: is the web container alive, is it responding quickly, and does the host still have enough resources? Every more complex dashboard grows from there.
