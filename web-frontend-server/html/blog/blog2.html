Why Docker Became the Gold Standard of DevOps

A container packages an app together with everything it needs to run, so “works on my machine” finally means “works in production” too.

Docker lets you package an application together with its runtime environment into a self-contained unit called a container. That all but eliminates the classic “it works on my machine but breaks in production” problem: what you test is exactly what you ship.

The problem Docker solves

An application is rarely just source code. It also depends on a language version, system libraries, environment variables and config files. A dev laptop on Node 20 and a server on Node 18 is enough to cause a bug that takes hours to track down. A container bundles all of that into an immutable image that runs the same way anywhere Docker is installed.

How containers differ from virtual machines

A virtual machine emulates an entire computer, including its own operating system. A container shares the host's kernel and only isolates processes, using Linux features such as namespaces and cgroups.

Aspect Virtual machine Container
Contents A full guest operating system Just the app and its libraries
Size Usually several GB Usually tens to hundreds of MB
Startup Minutes Seconds or less
Isolation Strong, at the virtual hardware level Process level, shared kernel
Density Dozens of VMs per host Hundreds of containers per host

Five concepts to know

  • Image: a read-only template made of stacked layers. Think of it as a “class”.
  • Container: a running instance of an image. Think of it as an “object”.
  • Dockerfile: the step-by-step recipe for building an image.
  • Registry: where images are stored, such as Docker Hub or a private registry.
  • Volumes and networks: keep data outside the container and connect containers to each other.

Hands-on: packaging this very website

The page you're reading is static HTML. A few lines are all it takes to put it in an Nginx container:

Dockerfile
FROM nginx:alpine
# Copy the static site into Nginx's default web root
COPY ./html/ /usr/share/nginx/html/
EXPOSE 80

Build it and run it:

Terminal
docker build -t myminicloud-web .
docker run -d --name web -p 8080:80 myminicloud-web
# Open http://localhost:8080 to see the site

Once a system has several services, Docker Compose describes them all in one file and starts them with a single command:

docker-compose.yml
services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"
    volumes:
      - ./html:/usr/share/nginx/html:ro
    restart: unless-stopped

Why mount it :ro?A read-only volume means the web container can't accidentally change or delete the site's content, even if it gets compromised.

Everyday commands

  • docker ps: list running containers.
  • docker logs -f web: follow the logs of the web container.
  • docker exec -it web sh: open a shell inside the container.
  • docker compose up -d and docker compose down: start and stop the whole stack.

Keeping images small and safe

  • Pick a small base image such as alpine or slim, and pin a specific version instead of latest.
  • Use a .dockerignore file so .git and node_modules never end up in the image.
  • Order your Dockerfile so rarely changing layers come first, to make the most of the build cache.
  • Don't run as root unless you have to, and never bake passwords into an image.
